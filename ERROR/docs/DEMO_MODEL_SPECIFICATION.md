# DEMO Model Specification

This document describes **only** the DEMO model pair (`demo_spoilage_risk_model.pkl` /
`demo_remaining_safe_time_model.pkl`, used when a request sets `model_mode: "demo"`).
It does not describe or change the REAL model pair, the ML pipeline, the BLE flow, the
firmware, or any other part of the application — this file is documentation only.

Everything below was produced by reading the actual code and dataset, and, where noted,
by running the actual trained `.pkl` files (not the label formula in isolation) through
`services/features.calculate_features()` and `predict.predict(mode="demo")` — the exact
same functions the live backend calls — to verify real behaviour rather than assume it.
Where the code's own comments disagree with what the code actually does, that is called
out explicitly rather than silently repeated.

Files inspected: `backend/scripts/generate_demo_dataset.py`, `backend/predict.py`,
`backend/services/features.py`, `backend/data/product_profiles.json`,
`backend/data/suraksha_dataset_demo.csv`, plus `backend/main.py` (only the narrow slice
that wires a `/sensor-data` request into `calculate_features()` → `predict()`, needed to
accurately describe how the documented files are actually invoked) and the two trained
`.pkl` files themselves (`model.feature_importances_`, read directly).

## 1. Dataset

| | |
|---|---|
| File | `backend/data/suraksha_dataset_demo.csv` |
| Generated by | `backend/scripts/generate_demo_dataset.py` |
| Rows | **55,305** data rows (55,306 lines including the header) |
| Columns | **27** (25 input features + 2 label columns) |
| Row breakdown by `product_type` | `refrigerated_medicine`: 18,546 · `room_temperature_medicine`: 18,524 · `vaccine`: 18,235 |

**It is synthetic, not real sensor logs.** `generate_demo_dataset.py` builds 220 synthetic
"shipment" trajectories per product type (660 total: 3 product types × 220), each between
20 and 150 steps long (`random.randint(20, MAX_STEPS)`, `MAX_STEPS = 150`), with each step
2 simulated seconds apart (`STEP_SECONDS = 2`, chosen to match the firmware's real
telemetry cadence) — so each trajectory covers up to 5 minutes. Random seeds are fixed
(`random.seed(42)`, `np.random.seed(42)`) for reproducibility.

Each synthetic shipment is randomly assigned one of four trajectory shapes:

| Shape | Weight | Behaviour |
|---|---|---|
| `stay_safe` | 30% | Temperature stays near a safe resting value the whole run (± small noise). |
| `ramp_and_hold` | 35% | Starts safe, jumps to an extreme ambient temperature partway through, and stays there. |
| `ramp_and_recover` | 25% | Starts safe, jumps to extreme, then returns to safe before the trajectory ends. |
| `already_hot_start` | 10% | Starts already at an extreme temperature. |

The "extreme" temperature in every shape is drawn from `AMBIENT_MIN_C = 19.0` to
`AMBIENT_MAX_C = 36.0` — deliberately chosen as *"achievable live-demo ambient range... a
hand cupped over the sensor or the room itself can realistically swing it through roughly
this band"* (the script's own comment), since there is no real refrigeration/heating
equipment available for a live demo.

**Every synthetic reading is run through the real, production `services.features.calculate_features()`
function** — the exact same function the live backend calls on real ESP32 telemetry — so
the 25 engineered features in the dataset are computed identically to how they would be
computed live, not approximated separately.

**Labels are not measured — they are computed by a hand-written formula**,
`demo_risk_and_safe_time()` in the same script, applied to each row's engineered features.
See section 4 for the exact formula. This is a critical distinction: the dataset does not
contain any ground-truth spoilage outcome; both target columns (`spoilage_risk`,
`estimated_remaining_safe_time`) are synthetic labels generated purely by that formula, and
the two RandomForest models are then fit to reproduce that formula's *output* from the 25
input features.

Verified label statistics (computed directly from the CSV):

| Column | min | 25% | 50% (median) | 75% | max | mean |
|---|---|---|---|---|---|---|
| `spoilage_risk` | 0.0 | 29.37 | 95.66 | 100.0 | 100.0 | 66.82 |
| `estimated_remaining_safe_time` | 0.0 | 0.0 | 1.19 | 103.2 | 180.0 | 52.16 |

Risk-level bucket counts across all 55,305 rows (using the same `< 30` / `< 70` / `>= 70`
thresholds `predict.py` uses live — see section 4): SAFE 13,851 · WARNING 7,933 ·
CRITICAL 33,521.

Reproducing the dataset/models: `pip install pandas numpy scikit-learn==1.9.0 joblib` then
`python generate_demo_dataset.py`, run from `backend/scripts/` (per the script's own
docstring). `scikit-learn==1.9.0` matches the pin in `backend/requirements.txt` — loading
the resulting pickles with a different scikit-learn version prints a version-mismatch
warning (harmless for these tree models, but worth keeping pinned).

## 2. Features / parameters

The DEMO model uses **the same 25-feature input schema as the REAL model** — both are
defined once, in `backend/models/feature_columns.json` and mirrored in
`predict.py`'s `FEATURE_COLUMNS`. `predict()` raises `ValueError("Missing required
features: ...")` if any of these 25 are absent, regardless of which mode is used.

| # | Feature | Type | Computed by |
|---|---|---|---|
| 1 | `product_type` | categorical (one-hot) | passed in directly |
| 2 | `min_temp` | numeric | product profile (section 3) |
| 3 | `max_temp` | numeric | product profile |
| 4 | `min_humidity` | numeric | product profile |
| 5 | `max_humidity` | numeric | product profile |
| 6 | `temperature` | numeric | raw reading |
| 7 | `humidity` | numeric | raw reading |
| 8 | `shock` | numeric | raw reading |
| 9 | `temperature_deviation` | numeric | `calculate_features()` — see section 5 |
| 10 | `humidity_deviation` | numeric | `calculate_features()` |
| 11 | `time_outside_temp_range` | numeric | `calculate_features()` — cumulative, per-shipment state |
| 12 | `time_outside_humidity_range` | numeric | `calculate_features()` — cumulative, per-shipment state |
| 13 | `temperature_rate_of_change` | numeric | `calculate_features()` — °C per elapsed minute since the last reading |
| 14 | `max_temp_deviation` | numeric | `calculate_features()` — cumulative running max, per-shipment state |
| 15 | `shock_count` | numeric | `calculate_features()` — cumulative count of readings with `shock >= 0.1` |
| 16 | `max_shock` | numeric | `calculate_features()` — cumulative running max |
| 17 | `cumulative_temp_exposure` | numeric | `calculate_features()` — Σ(deviation × elapsed minutes) while outside range |
| 18 | `cumulative_humidity_exposure` | numeric | `calculate_features()` — same, for humidity |
| 19 | `temperature_excursion_count` | numeric | `calculate_features()` — number of times temp transitioned into range→out-of-range |
| 20 | `time_since_first_excursion` | numeric | `calculate_features()` |
| 21 | `external_temperature` | numeric | live weather lookup (`main.py` → `get_weather()`), by GPS lat/lng |
| 22 | `external_humidity` | numeric | live weather lookup |
| 23 | `rain_probability` | numeric | live weather lookup |
| 24 | `wind_speed` | numeric | live weather lookup |
| 25 | `cooling_status` | numeric (0/1) | supplied by the caller in the request body (`SensorData.cooling_status`, default `0`) |

Both DEMO models are `sklearn.pipeline.Pipeline` objects: a `ColumnTransformer`
(`OneHotEncoder` on `product_type`, `"passthrough"` for the other 24 numeric columns) → a
`RandomForestRegressor(n_estimators=40, max_depth=8, min_samples_leaf=15, random_state=42)`
— one pipeline trained on `spoilage_risk`, a second identical pipeline trained on
`estimated_remaining_safe_time`.

### Which of the 25 actually drive the DEMO model's output — read directly from the trained `.pkl` files

`generate_demo_dataset.py`'s label formula (section 4) is written mainly in terms of
`temperature_deviation`. But that formula only decides the *training labels* — what
actually runs at inference time is the fitted RandomForest, and its real learned feature
importances (`model.feature_importances_`, read directly from the shipped `.pkl` files)
tell a different story:

**`demo_spoilage_risk_model.pkl`:**

| Feature | Importance |
|---|---|
| `cooling_status` | **0.8250** |
| `cumulative_temp_exposure` | 0.1456 |
| `temperature_deviation` | 0.0127 |
| `time_since_first_excursion` | 0.0072 |
| `time_outside_temp_range` | 0.0056 |
| `shock_count` | 0.0018 |
| `max_temp_deviation` | 0.0010 |
| `temperature` | 0.0007 |
| `max_shock` | 0.0004 |
| *(all other 16 columns, incl. the 3 `product_type` one-hot columns)* | 0.0000 |

**`demo_remaining_safe_time_model.pkl`:** same ranking — `cooling_status` **0.8520**,
`cumulative_temp_exposure` 0.0710, `temperature_deviation` 0.0640, everything else ≤ 0.005.

**In plain terms: `cooling_status` — not `temperature_deviation` — is by far the dominant
input to both trained DEMO models**, even though the label formula that produced the
training data does not add `cooling_status` to the score at all (see the code comment in
section 4). This happens because `cooling_status` is set identically, at both dataset-
generation time and live-inference time, as a **one-reading-lagged proxy for "was risk
already elevated a moment ago"**:

- At generation time, `generate_demo_dataset.py`'s own trajectory loop sets
  `cooling_status = 1 if risk >= 30 else 0` for the *next* row (`generate_demo_dataset.py`
  line ~222, comment: *"Mirror the real app's feedback loop: once risk crosses into
  WARNING territory, cooling kicks in for subsequent readings"*).
- At live inference time, the frontend does the same thing —
  `coolingStatusRef.current = result.prediction.cooling_required ? 1 : 0`, applied to the
  *next* `/sensor-data` POST (`SensorContext.jsx`; not one of this document's five source
  files, but it is the thing that supplies `cooling_status` on every real request, so it is
  named here for completeness).

Because that lag pattern is consistent between training and inference, "was
`cooling_status` 1 on the previous reading" turns out to be an extremely strong predictor
of "is risk elevated on this reading" in a smooth trajectory — strong enough that the
RandomForest leaned on it far more than on the deviation math it was nominally trained to
approximate.

**This was verified directly, not inferred from importances alone.** Feeding the same
large excursion (25 °C against a 2–8 °C vaccine range) through `calculate_features()` +
`predict(mode="demo")` with `cooling_status` forced to `0` on every single reading (i.e.
simulating a caller that never implements the feedback loop) produced:

```
t=0s   cumulative_temp_exposure=0.00  -> risk=34.83  WARNING
t=6s   cumulative_temp_exposure=1.70  -> risk=35.95  WARNING
t=30s  cumulative_temp_exposure=8.50  -> risk=35.95  WARNING
t=58s  cumulative_temp_exposure=16.43 -> risk=35.95  WARNING
```

Risk plateaus at ≈36 (WARNING) and **never reaches CRITICAL**, no matter how large
`cumulative_temp_exposure` grows or how long the excursion continues. With the
`cooling_status` feedback loop correctly implemented (as the live frontend already does),
the identical excursion reaches CRITICAL in 26 seconds (see section 10). **The
`cooling_status` feedback loop is load-bearing for the DEMO model to ever reach CRITICAL at
all** — this is not a hypothetical edge case, it is the single most important operational
fact about how this model actually behaves.

### Telemetry / UI data that is **not** part of the DEMO model's 25 features

| Field | Where it exists | Fed to the model? |
|---|---|---|
| `door`, `door_s` (lid open / duration) | Raw ESP32 packet | **No.** Not in `FEATURE_COLUMNS`. Handled entirely outside the ML pipeline (its own edge-triggered popup in the frontend). |
| `v_bat`, `bat_pct` (battery) | Raw ESP32 packet | **No.** Not in `FEATURE_COLUMNS`. Display-only. |
| `spd` (GPS speed), `dist` (ultrasonic cargo clearance) | Raw ESP32 packet | **No.** Not passed to `calculate_features()` at all. |
| `lat`, `lng` (GPS position) | Raw ESP32 packet | Indirectly only — used by `main.py` to call the weather service, whose *output* (`external_temperature`, `external_humidity`, `rain_probability`, `wind_speed`) is a feature. Raw lat/lng themselves are not. |
| `humidity`, `humidity_deviation`, `cumulative_humidity_exposure`, `time_outside_humidity_range`, `min_humidity`, `max_humidity` | In the 25-feature vector | **Structurally yes, practically no.** All show **0.0000** importance in both trained DEMO models (see table above). Verified directly: forcing humidity to 90% (well outside a 30–70% range) for 10 consecutive readings while temperature stayed perfectly safe produced `risk = 0.00 / SAFE` every single time. |
| `external_temperature`, `external_humidity`, `rain_probability`, `wind_speed` | In the 25-feature vector | **Structurally yes, practically no** — all **0.0000** importance in both trained DEMO models. |
| `shock` / `shock_count` | In the 25-feature vector | **Yes, a small real effect.** See section 8. |
| PCM flap / "coolant activated" (frontend UI) | Not a sensor input at all | **No separate input.** It is a pure *display* of the model's own `cooling_required` **output**, which is then fed back in as the *next* reading's `cooling_status` **input** (see the dominance discussion above). There is no independent PCM sensor reading anywhere in this pipeline. |

## 4. SAFE / WARNING / CRITICAL conditions

### Risk-level thresholds (`predict.py`, `get_risk_level()`)

These thresholds are **identical for REAL and DEMO mode** — `model_mode` only changes
*which model produces the risk score* fed into this function, not the thresholds
themselves:

```python
if risk < 30:      "SAFE"
elif risk < 70:     "WARNING"
else:               "CRITICAL"
```

i.e. **SAFE: risk < 30 · WARNING: 30 ≤ risk < 70 · CRITICAL: risk ≥ 70**.

### Label formula used to build the DEMO training data (`demo_risk_and_safe_time()`, `generate_demo_dataset.py`)

This is the formula that produced the CSV's labels. It is **not** re-run at live inference
time — at inference time the fitted RandomForest runs (see section 2's dominance finding)
— but it is what the model was trained to approximate, and it is exact, so it is
reproduced verbatim here:

```python
dev = feat["temperature_deviation"]        # instantaneous, see section 5
minutes = feat["time_outside_temp_range"]  # cumulative minutes outside range, see section 6

severity = 100.0 * (1.0 - math.exp(-dev / 3.2))
ramp = min(1.0, 0.35 + minutes / 1.25)
risk = severity * ramp

risk += min(8.0, feat["humidity_deviation"] * 0.25)   # capped secondary term
risk += min(12.0, feat["shock_count"] * 3.0)          # capped secondary term

risk = max(0.0, min(100.0, risk))

safe_time = max(0.0, 180.0 * (1.0 - risk / 100.0) ** 1.6)   # DEMO-only scale, 0-180
```

The script's own comment explains why `cooling_status` does **not** appear as a term here,
despite being a recorded feature: *"earlier drafts multiplied risk by 0.85 once
cooling_status == 1 ... removed: in a live hand-held demo nothing is actually cooling the
box, so that multiplier just put an artificial ceiling on how high risk could climb ...
cooling_status is still recorded as a feature (for consistency with the real model's
schema) but no longer suppresses the label."* (It nonetheless became the dominant learned
feature in the fitted models — see section 2.)

`severity` is a saturating curve: ≈50 at `dev = 2.2 °C`, ≈80 at `dev = 5 °C`, ≈95+ at
`dev ≥ 9 °C` (per the script's own comment, confirmed by the formula's arithmetic).

### Verified escalation timing (running the actual `.pkl` files, not just the formula)

All runs below used a real 2-second reading cadence, the same `calculate_features()` /
`predict(mode="demo")` call the live backend makes, and the `cooling_status` feedback loop
implemented correctly (matching the live frontend):

| Product / excursion | Deviation | First WARNING | First CRITICAL |
|---|---|---|---|
| vaccine (2–8 °C) → 25 °C | 17 °C | immediately (first out-of-range reading) | +26 s |
| room_temperature_medicine (15–25 °C) → 32 °C | 7 °C | immediately | +28 s |
| vaccine (2–8 °C) → 10 °C | 2 °C | +2 s | **never reached in 2 continuous minutes** (plateaued ≈35) |
| room_temperature_medicine (15–25 °C) → 27 °C | 2 °C | +2 s | **never reached in 2 continuous minutes** (plateaued ≈47) |

A small (~2 °C) deviation reliably reaches WARNING but does not, on the evidence gathered
here, escalate to CRITICAL on its own — CRITICAL requires a larger deviation and/or the
`cooling_status` feedback loop actively running (see section 2).

## 5. Temperature deviation — exact calculation

`services/features.py`, `calculate_temperature_deviation()`:

```python
if temperature < min_temp:
    return min_temp - temperature
if temperature > max_temp:
    return temperature - max_temp
return 0.0
```

This is `temperature_deviation` — always **≥ 0** (a magnitude), recomputed **fresh on every
call** from the current reading only. It is **not** accumulated or remembered between
readings.

This is distinct from `max_temp_deviation`, a separate feature tracked in per-shipment
state: `state["max_temp_deviation"] = max(state["max_temp_deviation"], temp_dev)` —
monotonically non-decreasing for the life of a shipment; it never goes back down even after
the temperature recovers. The DEMO label formula deliberately uses `temperature_deviation`,
not `max_temp_deviation` — the script's own docstring states this was an earlier draft's
actual bug: using `max_temp_deviation` "is exactly why testing showed the LED getting stuck
on red and the buzzer refusing to stop even after the box was back in a safe state — the
backend kept reporting CRITICAL forever because it was still scoring the worst moment of
the run, not the current one."

For comparison, `humidity_deviation` (`calculate_humidity_deviation()`) has an
**asymmetric sign**, unlike `temperature_deviation`:

```python
if humidity < min_humidity:
    return min_humidity - humidity   # positive
if humidity > max_humidity:
    return max_humidity - humidity   # NEGATIVE
return 0.0
```

Confirmed by direct test (humidity = 90%, `max_humidity` = 70 → `humidity_deviation =
-20.0`). This is a real, exact property of the code — noted here for completeness — but it
has no practical effect on DEMO predictions since the trained models place ~0 weight on
humidity regardless (section 2).

## 6. Time / duration behavior

`time_outside_temp_range` (per-shipment cumulative state, in **minutes**, only reset by
`reset_state(shipment_id)` / a fresh shipment — never decreases on its own while an
excursion is ongoing) feeds the label formula's `ramp` term:

```python
ramp = min(1.0, 0.35 + minutes / 1.25)
```

- At `minutes = 0` (the very first out-of-range reading): `ramp = 0.35` — a **partial**
  reaction is visible immediately.
- `ramp` reaches its ceiling of `1.0` when `minutes = (1.0 − 0.35) × 1.25 = 0.8125` minutes
  = **48.75 seconds**.

  **Note on a discrepancy in the code's own comment:** the docstring above this formula
  says *"full effect by ~75 seconds outside range"* — that does not match what the formula
  actually computes (48.75 s, worked out above). This document reports the formula's actual
  arithmetic, not the comment. The empirical CRITICAL-saturation time observed when running
  the real `.pkl` (risk plateauing near 99–100) landed at roughly 46–48 seconds outside
  range in the verification runs, which lines up with the 48.75 s figure, not 75 s.

Duration is **not** a hard gate before WARNING/CRITICAL can be reached — `ramp` only scales
severity, it doesn't block it. A large enough deviation reaches WARNING on the very first
reading (partial `ramp = 0.35` is already enough), and reaches CRITICAL as soon as
`severity × ramp ≥ 70`, which for a large deviation happens well before the 48.75 s
saturation point (e.g. 26 s in the verified 17 °C-deviation example in section 4).

## 7. Recovery behavior

Verified directly by running a full trajectory through `calculate_features()` +
`predict(mode="demo")`: safe → hot (through CRITICAL) → safe again, `cooling_status`
fed back correctly:

```
t=46s  temp=25.0  dev=17.00  cooling_status_in=1  -> risk=86.55  CRITICAL  cooling_required=True
t=48s  temp=25.0  dev=17.00  cooling_status_in=1  -> risk=86.68  CRITICAL  cooling_required=True
t=50s  temp=5.0   dev=0.00   cooling_status_in=1  -> risk=86.09  CRITICAL  cooling_required=False   <- temperature just recovered
t=52s  temp=5.0   dev=0.00   cooling_status_in=0  -> risk=0.00   SAFE      cooling_required=False   <- risk snaps to 0
```

- The moment temperature returns inside `[min_temp, max_temp]`, `temperature_deviation`
  becomes `0.0` immediately (it is recomputed fresh every call — see section 5).
- But `cooling_status` is fed into `calculate_features()` from the **previous** reading's
  `cooling_required` result (this is application-level behavior, mirrored identically by
  the real frontend's `coolingStatusRef`). So there is exactly a **one-reading lag**: the
  very first reading after recovering (`t=50s` above) still carries `cooling_status = 1`
  from the last hot reading, and the model still reports CRITICAL for that one reading —
  even though `temperature_deviation` is already `0`.
- On the **next** reading (`t=52s`, one telemetry interval later — 2 real seconds at 1×,
  proportionally faster under the frontend's TIME ACCELERATION control), `cooling_status`
  flips to `0` and risk **drops straight to `0.00` / SAFE** — not a gradual decay.

**Recovery, at the raw ML-prediction level, is effectively instantaneous** — delayed by
exactly one telemetry interval, not a multi-step ramp-down. This is a direct consequence of
`cooling_status` being the dominant learned feature (section 2): once it flips, the
prediction flips with it.

*(Out of scope for this document, but relevant context: the currently-shipped frontend
additionally holds the ESP32's red LED on for ~15 seconds after a CRITICAL episode clears,
specifically because the underlying model's own recovery is this abrupt. That hold is an
application/UX decision layered on top in `App.jsx`, not part of the DEMO model, its
training data, or this specification.)*

## 9. REAL vs DEMO model — why DEMO reacts faster

Both model pairs share the identical 25-feature input schema, the identical
`predict.py` risk-level thresholds (section 4), and the identical request pipeline
(`calculate_features()` → `predict(sensor_data, mode=...)`). The **only** difference is
which trained model pair `predict()` loads — selected per-request by the `model_mode`
field in the `/sensor-data` POST body (`SensorData.model_mode`, default `"real"`).

| | REAL model | DEMO model |
|---|---|---|
| Training data | Real cold-chain telemetry (`suraksha_dataset_corrected.csv` — not one of the five files this document was scoped to, so not independently re-verified here; referenced from the project's existing top-level `README.md`) | 660 synthetic 2–5 minute trajectories at achievable bench-test ambient temperatures (19–36 °C), this document's section 1 |
| Dominant learned feature | `cumulative_temp_exposure` (deviation × minutes accumulated) — per the project's existing `README.md` | `cooling_status` (this document, section 2) — **not** the deviation-based formula it was nominally trained to approximate |
| Why it reacts the way it does | Real shipments in the training data only ever showed large deviations after hours of *gradual* drift — there are no short-duration/large-deviation examples in that dataset, so the model learned that only sustained accumulated exposure indicates real risk | Training trajectories are short (≤5 min) and deliberately span the full deviation range quickly, so a real excursion is directly visible to the model almost immediately, amplified further by the `cooling_status` feedback loop |
| Time to escalate | Tens of minutes to hours for a sustained real excursion | Immediate partial reaction, WARNING on the first out-of-range reading for any but the smallest deviations, CRITICAL in roughly 25–30 seconds for a sizeable (≳7 °C) deviation, given `cooling_status` feedback (section 4) |
| Intended use | Production shipments | Live bench-test demos only — the model file itself and `predict.py`'s own comments say so explicitly: *"Never use 'demo' mode for a real shipment."* |

## 10. Demo examples

All figures below are from actual runs of the shipped `.pkl` files through
`calculate_features()` + `predict(mode="demo")`, at a real 2-second reading cadence, with
`cooling_status` fed back correctly (`cooling_status = 1 if previous cooling_required else
0`) — exactly matching what the live frontend already does.

**SAFE** — vaccine profile (2–8 °C), held at 5 °C: `temperature_deviation = 0`, `risk =
0.00`, `SAFE`, indefinitely, for as long as temperature stays in range.

**WARNING (reaches it, plateaus, never escalates)** — vaccine profile, excursion to 10 °C
(`dev = 2 °C`): risk ≈ 35 within 2 seconds of the excursion starting, and stays in the
WARNING band (never crosses 70) for at least 2 continuous minutes of sustained excursion in
the verification run.

**WARNING → CRITICAL** — vaccine profile, excursion to 25 °C (`dev = 17 °C`),
`cooling_status` feedback active:

| Elapsed since excursion started | Risk | Level |
|---|---|---|
| 0 s (first hot reading) | 36.3 | WARNING |
| 12 s | 54.9 | WARNING |
| 24 s | 68.6 | WARNING |
| **26 s** | **71.0** | **CRITICAL** |
| 38 s | 88.3 | CRITICAL |
| 46 s+ | ≈99.7 (saturated) | CRITICAL |

**CRITICAL → recovery** — same run, temperature returned to 5 °C at the 40-second mark of
continuous CRITICAL:

| Reading | Temp | Risk | Level |
|---|---|---|---|
| last hot reading | 25 °C | 86.7 | CRITICAL |
| **first recovered reading** | 5 °C | 86.1 | **CRITICAL** *(cooling_status still 1 from the previous reading — one-reading lag)* |
| **next reading (+2 s)** | 5 °C | 0.00 | **SAFE** *(cooling_status now 0 — snaps back, not gradual)* |

**Moderate excursion** — room_temperature_medicine profile (15–25 °C), excursion to 32 °C
(`dev = 7 °C`): WARNING immediately, CRITICAL at +28 s — comparable timing to the 17 °C
vaccine case above despite the smaller absolute deviation, because `severity = 100 × (1 −
e^(−dev/3.2))` is already ≈88% saturated by `dev = 7 °C`.

## Summary — exact answers

**Parameters used by the DEMO model (25, identical schema to REAL):** `product_type`,
`min_temp`, `max_temp`, `min_humidity`, `max_humidity`, `temperature`, `humidity`, `shock`,
`temperature_deviation`, `humidity_deviation`, `time_outside_temp_range`,
`time_outside_humidity_range`, `temperature_rate_of_change`, `max_temp_deviation`,
`shock_count`, `max_shock`, `cumulative_temp_exposure`, `cumulative_humidity_exposure`,
`temperature_excursion_count`, `time_since_first_excursion`, `external_temperature`,
`external_humidity`, `rain_probability`, `wind_speed`, `cooling_status`. Of these, the
fitted models actually rely almost entirely on **`cooling_status`** (82–85% importance),
with **`cumulative_temp_exposure`** and **`temperature_deviation`** a distant second and
third; everything else is ≤ 0.7% importance or exactly 0.

**Temperature ranges:** vaccine 2–8 °C · refrigerated_medicine 2–8 °C ·
room_temperature_medicine 15–25 °C (all: humidity 30–70%). Source: `product_profiles.json`.

**SAFE/WARNING/CRITICAL thresholds:** SAFE `risk < 30` · WARNING `30 ≤ risk < 70` ·
CRITICAL `risk ≥ 70` (`predict.py`, `get_risk_level()` — same thresholds for REAL and
DEMO).

**Duration requirements:** none are a hard gate. The label formula's time ramp
(`0.35 + minutes/1.25`, capped at `1.0`) reaches full effect at **48.75 seconds** outside
range (the code's own comment says "~75 seconds" — that does not match the formula's actual
arithmetic). A large deviation can reach CRITICAL well before that (26–28 s in the verified
examples) because `ramp` only scales severity, not gates it.

**Recovery condition:** temperature returning inside `[min_temp, max_temp]` zeroes
`temperature_deviation` immediately, but the model's actual output only follows one reading
later, once the `cooling_status` feedback (fed from the *previous* reading's
`cooling_required`) also flips to 0 — then risk drops straight to `0.00`/SAFE, not
gradually.

**Parameters NOT used by the DEMO model:** `door`/`door_s`, battery (`v_bat`/`bat_pct`),
GPS speed (`spd`), ultrasonic cargo clearance (`dist`), and raw GPS lat/lng (used only to
look up weather, not as a feature) are **not in the 25-feature vector at all**. Humidity
(`humidity`, `humidity_deviation`, and related cumulative/range fields) and all four
weather fields (`external_temperature`, `external_humidity`, `rain_probability`,
`wind_speed`) **are** in the 25-feature vector structurally, but the trained models place
**0.0000 importance** on every one of them — present in the schema, not actually used by
the fitted models. `product_type`'s one-hot columns are also `0.0000` importance directly
(it matters only indirectly, through the `min_temp`/`max_temp` it determines).
